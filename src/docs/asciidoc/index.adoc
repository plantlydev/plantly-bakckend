[[overview]]
== 개요

Plantly 서비스의 REST API 명세서입니다.
모든 응답은 아래 공통 래퍼(`ApiResponse`) 형태로 내려갑니다.

[[overview-response-wrapper]]
=== 공통 응답 형식

[cols="2,1,5"]
|===
| 필드 | 타입 | 설명

| `success` | `boolean` | 요청 성공 여부
| `message` | `string` | 성공 메시지 (성공 시, 없을 수 있음)
| `data`    | `object` | 응답 데이터 (성공 시, 없을 수 있음)
| `error`   | `string` | 에러 메시지 (실패 시에만 존재)
|===

NOTE: `ApiResponse` 는 `@JsonInclude(NON_NULL)` 이므로 값이 `null` 인 필드는 JSON 응답에서 생략됩니다.
예를 들어 회원가입 성공 응답에는 `data`/`error` 가 나타나지 않습니다.

[[overview-auth]]
=== 인증 / 보안 공통 규약

세션 기반 인증을 사용합니다. 인증 메커니즘은 전역 공통 규약이므로 각 API 문서에 반복하지 않고 여기에 한 번만 명시합니다.

* *로그인*: 운영은 소셜 로그인 전용입니다(<<social>> 참고). 로그인에 성공하면 `JSESSIONID` 세션 쿠키가 발급되고,
  이후 인증이 필요한 요청에는 이 세션 쿠키가 자동으로 동봉되어야 합니다.
  자체(이메일·비밀번호) 로그인 `POST /api/v1/auth/login` 과 회원가입 `POST /api/v1/users/sign-up` 은
  `app.auth.local-login-enabled=true` 인 환경(로컬·테스트)에서만 열리고, 운영에서는 `404 NOT_FOUND` 입니다.
* *CSRF*: 상태를 변경하는 모든 요청(`POST`, `PATCH`, `PUT`, `DELETE`)은 CSRF 보호를 받습니다.
  먼저 `GET /api/v1/auth/csrf` 로 토큰을 발급받은 뒤, 발급된 값을 `X-XSRF-TOKEN` 요청 헤더에 담아 보내야 합니다.
  누락 시 `403` 이 반환됩니다.
* *인증 실패*: 미인증 상태로 보호 자원에 접근하면 `401`, 권한이 부족하면 `403` 이 반환됩니다.

[cols="2,1,5"]
|===
| 항목 | 위치 | 설명

| `JSESSIONID` | Cookie | 로그인 시 발급되는 세션 쿠키 (인증 필요 API 필수)
| `X-XSRF-TOKEN` | Header | CSRF 토큰 (변경 요청 필수)
|===

[[social]]
== 소셜 로그인·가입

소셜 로그인은 API 가 아니라 브라우저 페이지 이동으로 진행됩니다(fetch 로 호출하지 않습니다).

. 로그인 버튼: 브라우저를 `/oauth2/authorization/naver` 로 이동시킵니다. 네이버 로그인 화면을 거쳐 콜백(`/login/oauth2/code/naver`)으로 돌아옵니다.
. 콜백 결과에 따라 백엔드가 프론트 화면으로 리다이렉트합니다.
+
[cols="3,4"]
|===
| 결과 | 이동

| 연결된 회원 — 로그인 완료(`JSESSIONID` 발급) | `/`
| 처음 온 사람 — 가입 대기 정보를 세션에 저장(10분 유효) | `/signup/social`
| 연결된 회원이 정지·탈퇴 상태 | `/login?error=ACCOUNT_SUSPENDED`
| 연결은 없고 같은 이메일의 회원이 있음 | `/login?error=EMAIL_IN_USE`
| 그 밖의 실패(취소, 제공자 오류 등) | `/login?error=SOCIAL_LOGIN_FAILED`
|===
. 가입 화면(`/signup/social`)은 아래 두 API 로 가입한 뒤, 응답의 `loginUrl` 로 브라우저를 이동시켜 로그인합니다.

두 API 는 로그인 전에 호출되며, 근거는 인증이 아니라 세션의 가입 대기 정보입니다. 가입 대기 정보가 없거나 만료되면 `401 SIGNUP_SESSION_EXPIRED` 이 반환되므로 로그인 화면으로 보내 소셜 로그인을 다시 시작합니다.

[[company]]
== 회사 (Company)

[[company-verification]]
=== 사업자 인증 (선행 인증)

회사 등록 *전에* 국세청 사업자등록정보로 사업자 진위를 확인합니다. 회원가입의 아이디 중복 확인처럼 등록 폼 앞단에서 먼저 수행합니다.

서버는 세 단계를 한 번에 처리합니다.

. *진위확인* — 사업자등록번호·대표자명·개업일자 조합이 국세청 등록 정보와 일치하는지 확인
. *상태조회* — 계속사업자인지 확인 (진위확인만으로는 폐업자를 걸러내지 못합니다 — 폐업해도 등록 이력이 남아 일치 판정이 납니다)
. *중복 검사* — 활성 회사 중 같은 사업자번호가 이미 있는지 확인

통과하면 `verificationId` 를 발급하고, 이 식별자를 <<company-create>> 요청에 실어 보내면 서버가 검증된 값을 채웁니다.
등록 요청에는 사업자번호·대표자명·개업일자 자리가 아예 없으므로, 인증받은 값과 다른 값이 저장될 수 없습니다.

CAUTION: `businessStartDate` 는 *개업일자* 입니다(사업자등록증 기준). 법인 등기 설립일과 다를 수 있으며, 국세청은 개업일자로만 대조합니다.

인증은 발급 후 *30분* 간 유효하며, 한 번 등록에 사용하면 재사용할 수 없습니다.
남용과 국세청 일일 쿼터 보호를 위해 사용자당 *하루 5회* 로 시도를 제한합니다(국세청 장애로 판정을 못 받은 시도는 차감하지 않습니다).

| 폐업자
| `400`
| 폐업한 사업자는 등록할 수 없습니다.

| `409`

| `429`

| `503`
| 국세청 시스템 점검 등으로 확인이 지연되고 있습니다. 잠시 후 다시 시도해주세요.

IMPORTANT: `503` 은 사용자 입력 문제가 아닙니다. 입력값을 고치라는 안내 대신 재시도를 안내해야 합니다.

[[company-reverification]]
=== 사업자 재인증

이미 등록·인증된 회사의 *대표자명·개업일자* 를 국세청에 다시 확인해 갱신합니다. 소유자(멤버)만 호출할 수 있습니다.

선행 인증(<<company-verification>>)과 결정적으로 다른 점은 *사업자번호를 요청으로 받지 않는다* 는 것입니다.
사업자번호는 DB 에 저장된 값(최초 인증본에서 온 불변값)을 그대로 국세청에 질의합니다 — 재인증 때 번호를 새로
입력받으면 오타나 타사 번호로 인증을 갈아끼워 "국세청 확인" 배지를 탈취할 수 있기 때문입니다. 국세청 연동은 그
회사의 존재·상태만 알려줄 뿐 소유권을 증명하지 않으므로, 번호는 절대 바뀌지 않게 고정합니다.

국세청 등록 정보가 바뀌었을 수 있으므로 서버는 이전 값과 비교하지 않습니다. 새로 입력한 대표자명·개업일자가
재확인을 통과하면 그대로 회사 정보를 덮어쓰고 인증 시각(`verifiedAt`)을 새로 찍습니다.

이 경로의 쓰임은 두 가지입니다.

. 국세청 정보(대표자명·개업일자)가 변경됐을 때의 갱신 창구. 국세청 인증을 받은 회사는 일반 수정(<<company-update-basic>>)으로
  이 두 값을 바꿀 수 없으므로(`400` 국세청 인증을 받은 회사는 대표자명·개업일자를 수정할 수 없습니다), 재인증을 통해서만 갱신합니다.
. 최초 인증 후 *1년* 이 지나면 재인증을 유도합니다(주기 갱신). 1년 경과를 감지해 재인증을 요청하는 이벤트 발행은 추후 과제이며,
  이 API 자체는 언제든 호출할 수 있습니다.

일일 시도 한도(사용자당 하루 5회)와 감사 로그는 선행 인증과 같은 집계를 공유합니다.

[[company-create]]
=== 회사 등록 (유저 자가등록)

인증된 유저가 본인 회사를 등록합니다. 등록자는 즉시 소유자(`OWNER`)가 됩니다.
변경 요청이므로 세션 쿠키와 CSRF 토큰이 필요합니다(<<overview-auth>> 참고).

자가등록은 <<company-verification>> 을 먼저 통과해야 하며, 발급받은 `verificationId` 를 함께 보냅니다.
등록이 완료되면 회사는 사업자 인증 완료(`businessVerified=true`) 상태로 생성됩니다.

NOTE: 요청 본문에 `businessNumber`/`ceoName`/`establishmentDate` 는 없습니다. 이 세 값은 인증 레코드에서만 채워지며,
`establishmentDate` 에는 국세청이 검증한 개업일자가 들어갑니다. 인증 후에는 대표자명·개업일자를 수정할 수 없습니다(<<company-update>>).

요청 본문은 회사 본체와 부속(연락처/이미지/레퍼런스/소재·설비·태그/링크 마스터 ID)을 한 번에 받습니다.
`companyName` 외 항목은 임시저장(DRAFT) 호환을 위해 모두 선택입니다.
컬렉션 개수 한도(카테고리 10개 · 상세 이미지 30장 · 레퍼런스 1건당 이미지 10장)는 모든 회사에 똑같이 적용되며,
넘기면 입력값 검증 실패(`400`)로 거부됩니다(<<meta-form-constraints>> 의 `maxItems`).

인증 식별자가 유효하지 않으면 등록이 거부됩니다 — 본인이 받은 것이 아니면 `400`(`VERIFICATION_NOT_FOUND`),
이미 다른 회사에 썼으면 `409`(`VERIFICATION_ALREADY_USED`).

유효기간(`expiresAt`)이 지난 인증은 거부하지 않습니다. 서버가 저장된 신원 값으로 국세청에 다시 확인해 갱신한 뒤
그대로 등록합니다(사용자 일일 인증 한도를 쓰지 않습니다). 이 확인에서 국세청이 휴업·폐업·불일치를 답하면 그 판정의
`400`(`VERIFICATION_SUSPENDED`·`VERIFICATION_CLOSED`·`VERIFICATION_MISMATCH`·`VERIFICATION_NOT_REGISTERED`)이,
국세청이 응답하지 않으면 `503`(`VERIFICATION_UNAVAILABLE`, 인증은 그대로 살아 있어 잠시 뒤 다시 누르면 됩니다)이 납니다.

=== 회사 등록 임시저장 (인증)

자가등록 폼을 작성하는 도중의 상태를 서버에 보관합니다. 발행(<<company-create>>) 전까지 *사용자·사업자번호당 1개* 가
유지되고, 발행이 성공하면 서버가 자동으로 지웁니다. 세션 쿠키가 필요하며, 저장·폐기는 변경 요청이라 CSRF 토큰도
필요합니다(<<overview-auth>> 참고).

* *키는 사업자등록번호입니다* (`verificationId` 가 아닙니다). 인증은 만료·재발급되며 식별자가 바뀌지만 작성 내용은 그
  수명에 묶이지 않습니다. 인증 식별자를 잃어버려도(기기 변경·저장소 초기화) 폼 첫 칸의 사업자번호만으로 이어 쓸 수 있습니다.
  하이픈은 있어도 없어도 됩니다(서버가 정규화합니다).
* *접근 권한은 인증 이력이 줍니다.* 본인이 그 번호로 사업자 인증(<<company-verification>>)을 통과한 적이 없으면
  `400`(`VERIFICATION_NOT_FOUND`), 번호 형식이 틀리면 `400`(`BUSINESS_NUMBER_INVALID_FORMAT`)입니다.
* *저장은 크기 상한만 검증합니다.* 부분 입력을 그대로 담으며, 필수값·형식·마스터 ID 검증은 발행 때만 합니다.
  다만 컬렉션 개수(태그 10개, 상세 이미지 30장 등)와 글자수(기업명 100자, 소개글 5000자 등) 상한은
  <<company-create>> 와 같은 값으로 검사해, 넘기면 `400` 입니다.
  본문은 <<company-create>> 의 요청과 같은 형태이고(컬렉션 포함), 모든 필드가 선택입니다.
* 복원한 `payload.verificationId` 는 저장 당시 값이라 낡았을 수 있습니다. 발행할 때는 조회 응답의
  `verification.verificationId` 로 덮어써 보내세요.
* *초안 자체에는 유효기간이 없습니다.* 인증 유효기간(`expiresAt`)이 지나도 저장·조회·발행이 막히지 않습니다 —
  발행할 때 서버가 저장된 신원 값으로 국세청에 다시 물어 갱신합니다. 사용자에게 다시 받을 값이 없으므로
  화면에 만료를 알릴 필요가 없습니다. 국세청이 실제로 휴업·폐업·불일치를 답한 경우에만 발행이 실패합니다.

=== 회사 목록/검색 (공개)

회사를 검색·브라우즈합니다. 누구에게나 열려 있는 공개 API 로, 인증이 필요 없습니다.

검색은 세 축으로 조합됩니다(모두 선택적, 지정한 것만 AND 로 적용):

* *통합 키워드* (`keyword`): 회사명·소개·레퍼런스·설비·소재 등 전체 텍스트에 부분일치. 공백으로 나눈 여러 토큰은 모두 포함(AND).
* *고급검색* (`companyName`/`content`/`reference` 등): 지정한 필드에만 부분일치.
* *패싯* (`certificationIds`/`industryIds`/`categoryIds`): 선택한 ID 중 하나라도 보유한 회사(차원 내 OR). 카테고리는 대분류를 고르면 그 후손 서브트리까지 매칭됩니다. 인증 패싯에 '기타'(`type=ETC`) 를 넣으면 이름을 무엇으로 적었든 직접 입력한 인증을 가진 회사가 모두 잡힙니다 — 검색은 마스터 ID 로만 매칭하고 입력한 이름은 보지 않습니다.

정렬은 스팟라이트 고정 → 추천 → 최신 순으로 고정이며, 결과는 요약 카드 형태로 페이징됩니다.

NOTE: 카드의 `spotlight` 는 *관리자가 수동으로 고정(pin)했는지* 를 뜻합니다. 메인 화면 노출 목록은 플래그로 거르지 말고
<<company-showcase>> 를 사용하세요(자리 수만큼 자르는 것은 서버가 정합니다).

=== 메인 화면 노출 영역 (공개)

메인 화면의 *스팟라이트* 와 *추천 기업* 두 영역을 한 번에 조회합니다. 누구에게나 열려 있는 공개 API 입니다.

목록/검색(<<company-search>>) 결과를 받아 프론트에서 플래그로 걸러내지 마세요 — 노출 후보가 화면의 자리 수보다
많아지는 순간 어느 회사가 잘릴지 프론트가 알 수 없고, 한쪽 영역이 통째로 비어 보일 수 있습니다.
어느 회사가 어느 자리를 차지하는지는 서버가 정해서 내려줍니다.

응답은 페이지가 아니라 *자리 수만큼의 고정 리스트* 라 `pageInfo` 가 없습니다. 각 영역의 자리 수는 서버 설정값입니다.

*스팟라이트 영역* 은 관리자가 고정(pin)한 회사(`spotlight = true`)이며, 관리자가 정한 순서(`spotlightOrder`)대로 담깁니다.

*추천 영역* 은 순수 관리자 큐레이션(`featured = true`)입니다.

두 영역에 같은 회사가 함께 나올 수 있습니다(고정 + 추천). 의도된 동작이므로 프론트에서 중복 제거하지 않습니다.

*카드 배경 두 필드*

카드에는 로고(`logoUrl`) 말고도 배경에 쓰는 값이 두 개 더 실립니다. 둘 다 선택이라 `null` 로 내려올 수 있고,
서버는 대체값을 만들어 주지 않습니다 — 없을 때 무엇을 그릴지는 화면이 정합니다.

* `coverImageUrl` — 카드 커버 사진. 로고와 다른 자리입니다(로고는 정사각 배지, 커버는 카드 배경에 깔리는 와이드 사진).
  같은 이미지가 스팟라이트(거의 정사각)와 추천 카드(가로로 긴 띠)에서 서로 다른 비율로 잘리므로 `object-fit: cover` 를 전제합니다.
  회사 갤러리(상세 응답의 `galleryImages`)와도 별개의 값입니다.
* `brandColor` — 스팟라이트 배너 배경색(`#RRGGBB`). 배너 위 텍스트 대비는 화면이 명도로 판단하세요.

=== 회사 기본 정보 수정 (소유자)

회사 멤버 본인이 자기 회사의 기본 정보를 부분 수정합니다. 변경 요청이므로 세션 쿠키와 CSRF 토큰이 필요합니다(<<overview-auth>> 참고).

본체 스칼라 필드만 수정하며, 부속 컬렉션(태그·소재·설비·연락처·이미지·레퍼런스·링크 마스터)은 <<company-update-collections>> 로 따로 교체합니다.

* *부분 수정(sparse)*: 모든 필드가 선택이며, 요청에 담긴 필드만 변경됩니다(`null`/미포함 = 미변경).
* *비우기(clear) 규약*: 선택 문자열 필드는 빈 문자열(`""`)을 보내면 값을 비웁니다. 필수 필드(회사명·대표자·주소 등)는 빈 문자열로 비울 수 없어 `400` 이 반환됩니다. 날짜·enum 은 비우기를 지원하지 않습니다(값이 오면 교체만).
* 시스템 플래그(`verified`/`featured`/`spotlight`/`spotlightOrder`/`deleted`)·사업자번호·등록 provenance 는 이 API 로 바꿀 수 없습니다(요청 필드에서 제외).
* `logoUrl` · `coverImageUrl` 은 둘 다 선택 필드라 `""` 로 비울 수 있습니다. 로고가 비면 화면은 회사명 앞 두 글자로 대체 배지를 그립니다(서버는 자리표시자 URL 을 만들지 않습니다).
* `brandColor` 는 `#RRGGBB` 형식만 받습니다(`""` = 비우기). 색 이름·축약형(`#RGB`)·`rgb()` 표기는 `400` 입니다.

수정 값은 이미 화면에 반영되어 있으므로, 성공 응답은 본문 없이 `success` 플래그만 내려갑니다.

=== 회사 부속 컬렉션 교체 (소유자)

회사 멤버 본인이 자기 회사의 부속 컬렉션을 *통째로 교체(PUT)* 합니다. 변경 요청이므로 세션 쿠키와 CSRF 토큰이 필요합니다(<<overview-auth>> 참고).

각 컬렉션은 독립된 엔드포인트로 나뉘며, 요청 본문의 리스트가 기존 컬렉션을 완전히 대체합니다(부분 수정이 아니라 전체 교체). *빈 배열(`[]`)을 보내면 해당 컬렉션을 전부 비웁니다.* 표시 순서(`displayOrder`)는 클라이언트가 보내지 않고 서버가 배열 인덱스로 재부여합니다. 성공 응답은 본문 없이 `success` 플래그만 내려갑니다.

[cols="3,4,4"]
|===
| 엔드포인트 | 본문 | 설명

| `PUT /api/v1/companies/{id}/tags` | `["문자열", ...]` | 태그명 목록
| `PUT /api/v1/companies/{id}/materials` | `["문자열", ...]` | 취급 소재명 목록
| `PUT /api/v1/companies/{id}/equipment` | `["문자열", ...]` | 보유 설비명 목록
| `PUT /api/v1/companies/{id}/contacts` | `[{연락처}, ...]` | 담당자 연락처 (현재 1건 제한)
| `PUT /api/v1/companies/{id}/images` | `[{이미지}, ...]` | 갤러리 이미지 (DETAIL 타입만 허용)
| `PUT /api/v1/companies/{id}/references` | `[{레퍼런스}, ...]` | 프로젝트 레퍼런스 (현재 1건 제한, 1건당 이미지 10장)
| `PUT /api/v1/companies/{id}/categories` | `[숫자, ...]` | 카테고리 ID 목록 (최대 10개)
| `PUT /api/v1/companies/{id}/certifications` | `[{인증}, ...]` | 인증 목록. 다른 링크와 달리 ID 배열이 아니라 `{"certificationId": 숫자, "customName": "문자열"}` 객체 배열입니다 (아래 참고)
| `PUT /api/v1/companies/{id}/industries` | `[숫자, ...]` | 산업군 ID 목록
| `PUT /api/v1/companies/{id}/countries` | `[숫자, ...]` | 수출 국가 ID 목록
| `PUT /api/v1/companies/{id}/regions` | `[숫자, ...]` | 국내 지역 ID 목록
|===

[NOTE]
====
*인증(`certifications`)만 본문 형태가 다릅니다.* 마스터 목록에 없는 인증을 회사가 직접 적어 넣을 수 있기 때문입니다.

* 목록에서 고른 인증: `{"certificationId": 3}` — `customName` 을 보내면 거부됩니다.
* 목록에 없는 인증: 공개 옵션 목록(`GET /api/v1/certifications`)의 *'기타'(`type=ETC`)* 항목 ID 를 보내고 `customName` 에 인증명을 적습니다. `customName` 없이 '기타'만 보내면 거부됩니다.
* '기타'는 이름만 다르면 여러 건 보낼 수 있습니다. 같은 인증 + 같은 이름은 1건으로 접힙니다(앞뒤 공백은 무시).
* 조회 응답의 `certifications[].certificationName` 에는 직접 입력한 이름이 그대로 실려 옵니다 — 프론트에서 '기타'와 입력값을 합칠 필요가 없습니다.

등록(`POST /api/v1/companies`)의 `certifications` 필드도 같은 형태입니다.
====

=== 회사 좋아요 / 즐겨찾기 (인증)

로그인한 사용자가 회사를 좋아요/즐겨찾기 하거나 해제합니다. 변경 요청이므로 세션 쿠키와 CSRF 토큰이 필요합니다(<<overview-auth>> 참고).

토글이 아니라 *등록(`PUT`)* 과 *해제(`DELETE`)* 로 동사를 분리했습니다. 덕분에 각 요청이 *멱등* 합니다 — 같은 요청을 여러 번 보내도 결과 상태가 한 방향으로만 수렴하며, 네트워크 재시도나 중복 클릭에도 안전합니다.

* 이미 좋아요/즐겨찾기한 상태에서 다시 `PUT` 을 보내도 오류가 아니라 `204` 로 응답합니다(서버가 중복 등록을 무시). 이미 도달한 상태를 재확인하는 것은 충돌이 아니므로 `409` 를 반환하지 않습니다.
* 없는 상태에서 `DELETE` 를 보내도 `204` 로 응답합니다.
* 성공 응답은 항상 본문 없는 `204 No Content` 입니다. 현재 상태(`likedByMe`/`favoritedByMe`)는 회사 조회 API(<<company-search>>, <<company-public-detail>>)가 내려주므로 이 API 는 본문을 되돌려주지 않습니다.

[cols="3,2,4"]
|===
| 엔드포인트 | 성공 | 설명

| `PUT /api/v1/companies/{id}/like` | `204` | 좋아요 등록 (멱등)
| `DELETE /api/v1/companies/{id}/like` | `204` | 좋아요 해제 (멱등)
| `PUT /api/v1/companies/{id}/favorite` | `204` | 즐겨찾기 등록 (멱등)
| `DELETE /api/v1/companies/{id}/favorite` | `204` | 즐겨찾기 해제 (멱등)
|===

아래는 좋아요 등록/해제를 대표 예시로 든 것입니다. 즐겨찾기(`/favorite`)도 경로만 다를 뿐 요청/응답 형태가 동일합니다.

[[upload-create]]
=== 이미지 업로드 (인증)

이미지 한 장을 올리고 조회 URL 을 받습니다. 회사 등록/수정 화면에서 파일을 고르는 *즉시* 호출하고, 응답의 `url` 을 폼 상태에 담아
`logoUrl` · `coverImageUrl` · `images[].imageUrl` 에 그대로 넣습니다. 임시저장(<<company-draft>>)에도 이 URL 문자열만 실립니다.
변경 요청이므로 세션 쿠키와 CSRF 토큰이 필요합니다(<<overview-auth>> 참고).

* 요청은 `multipart/form-data` 이고 파트 이름은 `file` 입니다. `Content-Type` 헤더는 직접 지정하지 말고 브라우저가 boundary 와 함께
  채우게 두세요.
* *한 요청에 한 장입니다.* 갤러리처럼 여러 장을 고르면 장마다 호출합니다 — 장별 재시도와 진행률이 따로 생깁니다.
* 이 API 는 파일을 URL 로 바꿀 뿐, 회사에 몇 장까지 붙일 수 있는지는 보지 않습니다. 장수 제한은 발행·수정 때 검사합니다.
* 올리기 전에 <<meta-upload>> 의 용량·형식으로 먼저 거르세요.

[cols="3,1,3"]
|===
| 사유 | 상태 | `code`

| `file` 파트 없음 | `400` | `FILE_REQUIRED`
| 허용하지 않는 형식 (실제 바이트 기준) | `400` | `UNSUPPORTED_IMAGE_TYPE`
| 용량 초과 (크게 넘으면 응답 대신 연결 끊김 — <<meta-upload>> 참고) | `400` | `FILE_TOO_LARGE`
| multipart 가 아닌 요청 | `415` | `UNSUPPORTED_MEDIA_TYPE`
| 서버 저장 실패 | `500` | `STORAGE_FAILURE`
|===

[[meta-form-constraints]]
=== 폼 입력 제약 조회

폼 하나에 걸린 입력 제약을 내려줍니다. 프론트가 저장을 누르기 전에 서버와 같은 기준으로 막고, 같은 문구를
띄우기 위한 것입니다. 값은 요청 DTO 에 붙은 검증 애너테이션에서 그대로 뽑으므로 서버가 실제로 강제하는
규칙과 어긋나지 않습니다. 세션 쿠키가 필요합니다(<<overview-auth>> 참고).

`fields` 는 화면의 폼 순서(요청 DTO 선언 순서)로 정렬돼 있고, `field` 이름은 검증 실패 응답의
`errors[].field` 와 같은 어휘입니다 — 폼을 그릴 때와 400 을 받았을 때 같은 키로 입력칸을 찾으면 됩니다.

==== 무엇이 실리고 무엇이 실리지 않는가

내려가는 것은 **우리가 정한 값**뿐입니다 — 필수 여부(`required`), 개수(`maxItems` · `minItems`),
길이(`maxLength` · `minLength`). 이 셋은 제품 결정이라 실제로 바뀝니다(로고는 필수에서 선택이 됐고,
주소 3필드는 반대로 선택에서 필수가 됐습니다). 프론트가 이 값을 들고 있으면 바꿀 때마다 두 곳이 어긋납니다.

**형식 규칙은 실리지 않습니다.** 사업자등록번호 10자리 · 우편번호 5자리는 국세청과 우정사업본부가 정한
형식이고 `#RRGGBB` · 이메일 표기도 마찬가지라, 우리 정책으로 바뀌는 값이 아닙니다. 이런 값은 클라이언트가
직접 알고 있으면 되고, 계약에 한번 넣으면 못 빼게 됩니다. 서버는 물론 그대로 강제하므로 놓친 형식 오류는
400 응답으로 되돌아옵니다.

그래서 **내려줄 규칙이 없는 칸은 목록에 아예 나오지 않습니다** — 제약이 없는 칸(enum 등)과,
형식 제약만 걸린 칸(등록 폼의 `businessNumber`, 수정 폼의 `postalCode` · `brandColor` · `establishmentDate`)입니다.

같은 이유로 회원가입 폼은 열지 않습니다. 비밀번호 규칙은 가입 화면이 "10자 이상, 특수문자 1개 포함" 같은
안내 문구로 어차피 화면에 적어야 하는 값이라, API 로 한 번 더 주면 같은 사실이 두 곳에 살게 됩니다.

==== 수정 폼을 쓸 때 주의할 점

`company-update` 는 **등록 폼과 제약이 다릅니다.** 수정은 sparse PATCH(안 보낸 필드 = 미변경)라
필수 규칙이 하나도 없고, 대신 빈 문자열로 지울 수 없는 칸에 `minLength: 1` 이 붙습니다. 이 차이는
PATCH 의미론에서 오는 것입니다 —
**등록 폼의 제약을 수정 화면에 재사용하면 미변경으로 두어도 되는 칸을 필수로 막게 됩니다.**

또한 `company-update` 에는 **본체 스칼라만** 담깁니다. 수정 화면의 컬렉션(태그 · 소재 · 카테고리 등 11종)은
각자의 교체 PUT 엔드포인트로 가고 그 제약은 이 응답에 나오지 않습니다. 개수 상한 값 자체는 등록 경로와
같으므로 등록 폼 응답(`company-create` / `my-company-create`)의 컬렉션 상한을 그대로 보면 됩니다.

컬렉션 개수 상한(카테고리 개수 · 이미지 장수)은 회사마다 다르지 않습니다. 자가등록 · 수정 · 관리자 등록 폼 모두
이 응답의 `maxItems` 가 유일한 근거입니다.

프론트가 폼을 막는 근거는 이 밖에 하나 더 있습니다. 중복 여부(이메일 · 사업자번호)는 값을 봐야 알 수 있어
사전 검증이 불가능하므로, 전용 확인 엔드포인트를 왕복합니다.

=== 고정 선택지 카탈로그 (공개)

서버 enum 으로 정해진 선택지(기술성숙도 · 견적 산출방식 등)의 값과 화면 문구를 한 번에 내려줍니다.
공개 회사 상세도 `trlLevel: "MASS_PRODUCTION"` 을 "양산 적용 가능" 으로 그려야 하므로 *인증 없이* 열려 있습니다.

* 키는 요청 DTO 의 필드 이름입니다. 폼 제약(<<meta-form-constraints>>)의 `fields[].field`, 검증 실패의 `errors[].field` 와
  같은 어휘라 같은 키로 이어 붙이면 됩니다.
* `value` 는 요청·응답에 오가는 값이고, `label` 은 화면에 그대로 쓰는 문구입니다. 프론트가 문구를 따로 짓지 않습니다.
* 사용자가 고르지 않는 값(인증 그룹 · 대륙)은 실리지 않습니다. 이런 값의 표기는 화면이 정합니다.
* 낱개 조회 경로는 없습니다. 전부 합쳐도 작고 사실상 바뀌지 않으므로 폼을 열 때 한 번 받아 두세요.

[[meta-upload]]
=== 이미지 업로드 제약 조회

이미지를 고르는 순간 프론트가 스스로 막을 근거입니다. 한 장당 최대 용량과 허용 형식을 내려줍니다.
업로드(`POST /api/v1/uploads`) 자체가 로그인을 요구하므로 이 조회도 세션 쿠키가 필요합니다(<<overview-auth>> 참고).

==== 용량 (`maxFileSizeBytes`)

* *배포마다 다른 값입니다.* 환경변수로 조정되므로 화면에 하드코딩하지 마세요. 바이트 단위라 `File.size` 와 그대로
  비교하면 되고, "10MB" 같은 표기는 화면이 만듭니다.
* 서버의 요청 상한도 이 값에서 만들어지므로, *이 크기 이하의 파일은 용량 때문에 거절되지 않습니다.*
* *넘는 파일은 반드시 올리기 전에 막으세요.* 조금 넘으면 `400`(`FILE_TOO_LARGE`)이 오지만, 크게(수 MB 이상) 넘으면
  서버가 본문을 끝까지 받지 않고 연결을 닫습니다. 이때 클라이언트는 응답 대신 네트워크 오류를 받습니다.

==== 형식 (`allowedContentTypes` · `allowedExtensions`)

* 서버는 파일명과 `Content-Type` 을 보지 않고 *실제 바이트로 형식을 판별*합니다. 최종 판정은 서버가 하므로,
  프론트의 사전 검사는 *서버가 받을 파일을 막지 않는 선에서만* 쓰세요.
* `<input accept>` 에는 `allowedContentTypes` 를 넣으면 됩니다. MIME 타입을 주면 운영체제가 확장자 별칭까지 묶어 보여줍니다.

*장수* 제한은 여기 없습니다. 폼 제약(<<meta-form-constraints>>)의 `maxItems` 를 보세요. 이 응답은 "한 장당" 제약입니다.
